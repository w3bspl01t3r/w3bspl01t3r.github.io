CommonsBeanUtils1

If you’re reading this for the first time, I’d recommend going through the CommonsCollections blogs first and then coming back here. This series is built on top of the CommonsCollections series.

In this blog post we’ll discuss the CommonsBeanUtils1 gadget: how it works, why the dependencies matter, and we’ll wrap up with a safe “local lab” discussion (non-operational) to show the control flow end-to-end.

Safety note: This post intentionally avoids publishing weaponizable exploit code (for example, deserialization payloads that execute OS commands). The goal here is to explain the mechanics and the defensive implications.

Quick refresher: CommonsCollections2 control flow

For refresher, CommonsCollections2 is commonly described with a control-flow chain like: 

PriorityQueue.readObject()
  → PriorityQueue.heapify()
    → PriorityQueue.siftDown(...)
      → Comparator.compare(...)
        → (Comparator-specific logic)
          → TemplatesImpl.newTransformer()
            → loads attacker-controlled bytecode (if present)

The key learning: PriorityQueue deserialization re-orders elements during readObject(), and if a non-null comparator exists, it will be invoked while heapifying.

CommonsBeanUtils1: what changes at a high level?

CommonsBeanUtils1 is conceptually very similar to CC2 in that it leverages: PriorityQueue + a Comparator, and reaches a sensitive method on a JDK/Xalan class (often described as TemplatesImpl).

The main change is: instead of a comparator that transforms objects via an “invoker-style” transformer, this gadget uses BeanComparator. 

PriorityQueue.readObject()
  → PriorityQueue.heapify()
    → PriorityQueue.siftDown(...)
      → BeanComparator.compare(...)
        → property resolution via PropertyUtils.getProperty(...)
          → getter resolution via JavaBeans Introspector
            → (sensitive method reachable in vulnerable configurations)
Note: If you’re unsure why passing a comparator matters, revisit the CC2 post: the moment PriorityQueue heapifies during deserialization, it will call compare() on the comparator.

Deep dive: BeanComparator.compare()

When we initialize a BeanComparator like: 

BeanComparator bc = new BeanComparator("outputProperties");

It sets two important fields:

  • property gets set (e.g., "outputProperties").
  • comparator is set to a default comparable comparator if not supplied. (This is where transitive dependencies can come into play.)

Inside compare(o1, o2), when property is non-null, it resolves: 

value1 = PropertyUtils.getProperty(o1, property);
value2 = PropertyUtils.getProperty(o2, property);
return internalCompare(value1, value2);

The critical part is PropertyUtils.getProperty. Because you control:

  • o1/o2 (objects placed into the queue), and
  • property (the string passed to the comparator),

you influence which getter method is discovered and invoked through the JavaBeans introspection process (property descriptors, read methods, etc.).

How property resolution works (conceptually)

For simple properties (not nested like a.b.c), the resolution typically:

  1. Creates/uses introspection data for the target class.
  2. Finds a matching property descriptor for the supplied property name.
  3. Extracts a read method (getter) from the descriptor.
  4. Invokes the read method reflectively.

That’s why a property name like outputProperties maps to a getter like getOutputProperties() when present and compatible with JavaBeans rules.

“Quick Question” section (safe answer)

Q: “Where do we send getOutputProperties() to invokeMethod?”

In JavaBeans-style introspection, you usually don’t pass the method directly. You fetch a PropertyDescriptor, then call something like getReadMethod() on it to obtain the getter method, and only then invoke it. So the “method reference” is derived from metadata, not hard-coded.

Dependencies: why three jars show up in many writeups

1) commons-logging

Commons Logging is often a compile/runtime dependency of BeanUtils. In many environments, BeanUtils may throw errors if it cannot find commons-logging on the classpath, even if logging isn’t directly involved in the gadget chain.

2) commons-collections

Some BeanComparator constructors or defaults can reference comparator utilities that live in Commons Collections. In some cases, this dependency is incidental to the chain and can be replaced by supplying your own comparator (as long as it’s compatible and serializable where needed).

3) commons-beanutils

This is the core library providing BeanComparator/PropertyUtils property resolution logic.

Defensive takeaway: A “not used directly” dependency can still matter because it changes what classes are available at runtime and what defaults get selected. Always model the full classpath when assessing deserialization risk.

Defensive checklist: how to reduce risk

  • Disable Java native deserialization for untrusted data wherever possible.
  • Use an allowlist-based ObjectInputFilter (JEP 290) to restrict classes during deserialization.
  • Remove unused libraries (BeanUtils / Collections / Xalan) from server classpaths when not required.
  • Patch/upgrade libraries and runtimes, and track known gadget-bearing versions.
  • Add detections: look for suspicious deserialization entry points and unexpected PriorityQueue/Comparator usage patterns.

Summary

  • CommonsBeanUtils1 follows the same deserialization “entry point” pattern as CC2: PriorityQueue.readObject() triggers heap operations.
  • The comparator’s compare() is invoked during heapify/sift-down, making comparators powerful gadget primitives.
  • BeanComparator resolves a property name into a getter call via JavaBeans introspection (PropertyDescriptor → getReadMethod() → reflective invoke).
  • Some dependencies appear due to transitive/default behaviors (logging / default comparators), even if not central to the vulnerable control flow.
  • Best defense is to avoid deserializing untrusted data and enforce strict class filtering (JEP 290).
